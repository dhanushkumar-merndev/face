- Expects the agent to handle infra/ops tasks directly: reading the project `.env`, running DB migrations (e.g., `db push`), and validating environment configuration end-to-end with the real credentials in `.env` (e.g., actually testing Tigris connectivity/write access with the keys), proactively surfacing and fixing env gaps (missing bucket name, empty secrets) rather than just handing the user instructions to run. Confidence: 0.8
- Uses Tigris Data (https://www.tigrisdata.com) as the object-storage backend instead of real AWS S3, and expects the codebase to support it via the S3-compatible endpoint (region "auto", virtual-hosted style) while keeping AWS services (e.g. Rekognition) where required. Confidence: 0.9
- Wants the repo's `.env.example` kept complete and self-documenting: every required env var listed, with comments explaining what it does, example/filled values (e.g. `AWS_S3_BUCKET=face`), and generator commands for secrets that must be randomly produced. Confidence: 0.85
- Keeps live credentials and secrets (e.g., the Supabase session-pooler `DATABASE_URL` with the real password) strictly in `.env` — explicitly "not example env" — so the `.env.example` stays a template with no real secrets. Confidence: 0.9

Confidence: 0.9
- Prefers email/password admin authentication with a provisioned, known admin account (explicitly requested `admin@gmail.com` / `Face@admin123` created via a `seed:admin` script) over OAuth flows for the MVP, accepting hardcoded dev credentials even though they are insecure for production. Confidence: 0.8
